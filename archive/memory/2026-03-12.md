What the sweep does:
- reruns the real measured multiseed boundary-aware benchmark for `boundary_weight in {1, 2, 4, 8}`
- evaluates pooled active-boundary semantic accuracy, pooled change recall, and mean active-boundary regret
- computes a Pareto frontier:
  - maximize active-boundary accuracy
  - maximize local oracle-change recall
  - minimize active-boundary regret

Key MPS result:
- Pareto frontier is only:
  - `weight=2`: `63.7%` active-boundary accuracy, `7.48%` regret, `28.6%` change recall
  - `weight=4`: `70.8%` active-boundary accuracy, `2.33%` regret, `27.3%` change recall
- interpretation:
  - MPS does not have one universally best weight
  - `4` is the clean balance point
  - `2` is the higher-recall alternative
  - `8` is too costly and collapses recall back down

Key CPU result:
- Pareto frontier is:
  - `weight=1`: `64.9%` active-boundary accuracy, `14.96%` regret, `31.1%` change recall
  - `weight=4`: `63.8%` active-boundary accuracy, `10.43%` regret, `21.5%` change recall
  - `weight=8`: `48.4%` active-boundary accuracy, `19.40%` regret, `31.7%` change recall
- interpretation:
  - CPU keeps a broader frontier
  - `1` and `4` are the practical operating points
  - `8` is technically Pareto but probably too costly to recommend

Main claim update after sweep:
- the repo should stop treating `boundary_weight=4` as intrinsically special
- the stronger claim is:
  - measured boundary-aware retraining can be qualified as a backend-specific operating-point choice
  - there is no single backend-independent best weight
  - boundary sensitivity is tunable, but still requires explicit regret/recall tradeoff selection

What the sweep does:
- reruns the real 5-seed multiseed benchmark for pairwise configs:
  - `0.5:0.0`
  - `1.0:0.0`
  - `1.0:0.25`
  - `2.0:0.25`
- compares them against baseline and weighted CE on active-boundary accuracy, regret, and change recall

Important finding:
- this sweep is useful, but noisier than the weight sweep because every point reruns real profiling and labels a fresh oracle bank
- the frontier is therefore exploratory rather than citation-grade

Current MPS frontier from the exploratory sweep:
- `baseline`: `66.2%` active-boundary accuracy, `3.73%` regret, `32.2%` change recall
- `transition_weight=1, transition_same_weight=0.25`: `75.0%`, `2.40%`, `17.1%`
- `transition_weight=0.5, transition_same_weight=0`: `74.8%`, `1.98%`, `8.5%`

Current CPU frontier from the exploratory sweep:
- `transition_weight=1, transition_same_weight=0.25`: `53.6%`, `15.63%`, `16.7%`
- `baseline`: `64.6%`, `12.03%`, `13.0%`
- `weighted_ce`: `64.6%`, `11.60%`, `11.3%`
- `transition_weight=0.5, transition_same_weight=0`: `67.2%`, `11.94%`, `5.2%`

Interpretation:
- there is no clean pairwise-objective winner under the current sweep protocol
- the main outcome is methodological:
  - objective-level sweeps need a frozen per-seed oracle bank
  - otherwise each config is compared on a fresh measured profile set and the frontier becomes noisy
